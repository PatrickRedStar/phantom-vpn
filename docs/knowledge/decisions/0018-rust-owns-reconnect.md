# 0018 — Rust — единственный владелец переподключения; error = фатально

## Context

Аудит 2026-10-22 ([отчёт](../audits/2026-10-22-full-scan.md), П1, П2, П3, А1)
показал, что за переподключение отвечали сразу несколько слоёв и мешали друг
другу:

- **Ядро сдавалось насовсем.** `supervise` переходил в `Error` после 8 неудач
  подряд за сессию, а без сети эти 8 попыток сгорали за ~2 минуты. На iOS, Linux
  и OpenWrt туннель после этого оставался «поднятым», а трафик уходил в никуда до
  ручного «Повторить».
- **Обёртки строили своих сторожей поверх ядра.** На Android Kotlin-watchdog
  через 3 с не-`connected` перезапускал нативный туннель, хотя Rust уже
  переподключался сам. Каждая смена сети давала два полных залпа по N
  рукопожатий подряд, а такой залп проект сам считает VPN-отпечатком. Наличие
  сети сторож смотрел через `activeNetwork`, то есть при поднятом TUN — через сам
  VPN, и после долгого обрыва засыпал навсегда. Если Android всё-таки сдавался,
  TUN снимался, и трафик шёл мимо VPN. На macOS провайдер держал таймеры «30 с без
  connected» и «120 с в reconnecting» и гасил или перезапускал туннель поверх
  ядра.
- **Один умерший стрим из N не восстанавливался** до конца сессии: ядро
  реагировало, только когда мертвы все. Попытка v0.27.0 рвать всю сессию при
  любом мёртвом стриме давала синхронный залп и была откачена в v0.27.1.
- **`Error` ничего не значил.** Классификатор видел только верхнюю строку ошибки,
  отзыв доступа выглядел как обычный обрыв (клиент переподключался вечно), а
  сетевые ошибки после 8 попыток превращались в «фатальные».

## Decision

**Переподключением владеет только ядро (`client-core-runtime`); `error` — только
для ошибок, которые ретраем не лечатся, с понятной причиной.**

1. **Бесконечный ретрай** при `auto_reconnect`: пауза по категории ошибки
   (1 с после RST, 2 с после тишины, 3 с после DNS, 5 с без сети или после
   TLS-алерта), пол — `BACKOFF_SECS = [1, 2, 5, 10, 20, 30]`, джиттер до +25 %.
   Счётчик сбрасывается после сессии, прожившей ≥ 30 с. `Reconnecting`
   публикуется сразу после обрыва, отмена во время паузы — `Disconnected` без
   ошибки.
2. **Переоткрывается только умерший стрим**: одно соединение с тем же
   handshake, случайная пауза 1–10 с, сервер пристыковывает его к живой сессии по
   fingerprint. Вся сессия переподключается, только если мертвы все N (≥ 3 с),
   после сна устройства (скачок wall-clock > 60 с) или при фатальной ошибке.
   Любой мёртвый стрим = `Degraded`. Stale — 75 с без любого кадра, мёртвый
   стрим — 90 с (heartbeat считается).
3. **Фатальны** (`ConnState::Error`, причина в `last_error`, ретраев нет):
   алерт сервера `certificate_revoked` / `access_denied` («Доступ отозван»),
   `certificate_expired` («Срок действия доступа истёк»), ошибки дат серта
   сервера («проверьте дату и время на устройстве»), кривой профиль, закрытый
   TUN. Чужой серт сервера (неизвестный издатель, не то имя, `BadCertificate`)
   **не** фатален: так выглядят captive portal и fallback-серт реле. Чтобы отзыв
   доходил алертом, после соединения короче 30 с клиент идёт полным хендшейком,
   без resumption (на resumed-сессии сервер серт не проверяет).
4. **Обёртки реагируют только на `error` и действия пользователя**:
   - Android: Kotlin-сторож удалён. При потере связи TUN не снимается и
     блокирует трафик (kill switch); через 25 с без связи уведомление «Нет
     связи» с кнопкой «Отключить». TUN снимается только по Disconnect, onRevoke
     или фатальной ошибке, причина которой показывается на дашборде и в
     уведомлении. Адрес сервера Kotlin резолвит сам через физическую сеть, в
     Rust имя не уходит.
   - macOS / iOS: watchdog'и провайдера удалены. На `error` провайдер
     останавливает туннель, error-кадр остаётся в снапшоте и на экране до
     следующего Connect.
   - Linux GUI/helper и CLI: ядро как есть.

## Alternatives considered

1. **Оставить Kotlin/Swift-сторожей, но перед рестартом перечитывать состояние
   ядра** (минимальный вариант из аудита). Отклонено: два владельца одного
   процесса всё равно гоняются друг с другом, а залп рукопожатий при смене сети
   остаётся. Удаление кода проще и честнее.
2. **Лимит попыток, но побольше (или «сбрасывать по сигналу сети»).** Отклонено:
   у ядра нет надёжного сигнала «сеть вернулась» на всех платформах, а любой
   лимит в метро заканчивается тем же мёртвым «подключено».
3. **Рвать всю сессию при любом мёртвом стриме** (v0.27.0). Отклонено ещё в
   v0.27.1: синхронный залп из N рукопожатий — DPI-признак. Точечное
   переоткрытие одного стрима залпа не даёт.
4. **Снимать TUN при долгом отсутствии связи** (прежнее поведение Android).
   Отклонено: это fail-open — трафик молча уходит мимо VPN. Пользователь, которому
   нужен интернет без VPN, жмёт «Отключить».
5. **Понизить число стримов, чтобы реже умирали.** Отклонено: N = ядрам —
   инвариант проекта; устойчивость решается переоткрытием, а не уменьшением N.

## Consequences

**Плюсы:**
- Клиент без ручного «Повторить» переживает метро, сон и смену сети.
- Один залп рукопожатий на событие вместо двух; мёртвый стрим не тащит за собой
  сессию.
- `error` снова значит «нужно действие пользователя», а причина видна.
- На Android нет fail-open: без связи трафик блокируется, а не утекает.

**Минусы / tradeoffs:**
- Без связи Android-телефон остаётся без интернета, пока пользователь не нажмёт
  «Отключить». Это сознательный выбор в пользу kill switch.
- Без сети ядро продолжает пробовать раз в ~30 с. Пакетов это почти не даёт, но
  ретраи идут, пока пользователь не отключится.
- Linux CLI тоже ретраит бесконечно и завершается только на фатальной ошибке
  (код ≠ 0, причина в stderr): `Restart=` у systemd на сетевых обрывах не
  срабатывает. OpenWrt-клиент собран на `client-common` без
  `client-core-runtime`: ретраит бесконечно сам (пауза до ~30 с), а отзыв и
  истёкший серт для него не фатальны — роутер должен подниматься сам.

**Что открывает:**
- Детект сна и TCP_USER_TIMEOUT в ядре — одна правка для всех платформ.

**Что закрывает:**
- Новые сторожа переподключения в обёртках. Если платформе нужно реагировать на
  сеть, она сообщает ядру событие, а не перезапускает туннель.
