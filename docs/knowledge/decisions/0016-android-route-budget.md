# 0016 — Бюджет маршрутов VPN на Android считается по чужим процессам

- **Статус:** принят
- **Дата:** 2026-08-01
- **Зона:** `crates/core/src/routing.rs`, `apps/android/.../GhostStreamVpnService.kt`

## Контекст

Системное приложение Настройки падало при открытии Подключения → Другие
настройки — но только при поднятом нашем туннеле, на Fold 8 и Z Flip.

Замер на Galaxy Z Fold 8 при включённом «обходе списков» с российским списком:

```
маршрутов на tun0:                 7982
LinkProperties VPN-сети (dumpsys): 295 086 символов (≈940 КБ в parcel)
```

Стек падения Настроек:

```
libbinder: Binder transaction failure ... error: -28 (Binder buffer full)
JavaBinder: !!! FAILED BINDER TRANSACTION !!! (parcel size = 96)
TransactionExecutor: Failed to execute ... LaunchActivityItem ... SubSettings
AndroidRuntime: FATAL EXCEPTION: DeadSystemException
```

`MAX_VPN_ROUTES = 8000` подбирался под лимит **одной** Binder-транзакции в
`VpnService.establish()` — 8000 маршрутов туда влезают. Но тот же список уезжает
в `LinkProperties` VPN-сети, а её читает **любой** процесс через
`ConnectivityManager`, и там действует per-process лимит буфера (~1 МБ).
7982 × ~120 Б ≈ ровно этот мегабайт: буфер Настроек забивается целиком, и падает
уже следующая 96-байтная транзакция запуска активити.

Под удар попадает не только Настройки — то же получает любое приложение,
читающее состояние сети (антифрод, детекторы VPN).

## Решение

**Бюджет структуры, которую отдают наружу, считается по самому слабому
потребителю, а не по собственному вызову.** Введён `ANDROID_ROUTE_BUDGET = 1500`
(≈17 % лимита) вместо потолка 8000.

Чтобы уложиться, комплемент не урезается выбрасыванием direct-записей, а
**склеивается**: соседние туннельные блоки объединяются, проглатывая дырки
до /17 (32 768 адресов). Порог адаптивный — удваивается, пока не влезем.

Направление жертвы выбрано осознанно: расширяется **туннель**, не direct.
Проглоченная дырка — российская подсеть, которая поедет через выход вместо
прямого доступа; ни один не-российский адрес наружу не выходит. Обратное
направление (округление direct-списка) запрещено — именно это убрал коммит
dd94139b, там лишний адрес молча теряет защиту.

Спец-диапазоны (private, loopback, link-local, CGNAT, multicast) вырезаются
**повторно после** склейки: широкий порог может их накрыть, а датапас такие
пакеты не доставит — отвалился бы LAN.

### Замеры на настоящем `ru.txt` (12 813 IPv4-блоков)

| Порог дырки | Маршрутов | RU напрямую | Parcel |
|---|---|---|---|
| точный комплемент | 29 961 | 100 % | ~3.4 МБ |
| /20 | 6 774 | 85.3 % | 793 КБ |
| /18 | 2 561 | 64.8 % | 300 КБ |
| **/17 (выбран)** | **1 417** | **52.3 %** | **166 КБ** |
| /16 | 741 | 39.8 % | 86 КБ |

Для сравнения, грубое огрубление префиксов (floor) при 631 маршруте даёт лишь
37.3 % — склейка выигрывает тем сильнее, чем больше бюджет.

## Заодно закрыт fail-open

Пустой комплемент (direct-список накрывает `0.0.0.0/0` или /1../7) раньше
означал ноль IPv4-маршрутов: `establish()` проходил, статус показывал
«Подключено», а весь IPv4 шёл мимо туннеля открытым текстом. Теперь пустой
набор → полный туннель.

## Дубль в Kotlin — временный

Склейка написана и в `routing.rs`, и в `GhostStreamVpnService.kt`, потому что в
репозитории лежит prebuilt `libphantom_android.so`, а NDK есть не на каждой
машине разработки. Kotlin-версия работает с текущим `.so`. **Снять дубль после
первой пересборки `.so`** — оставлять два генератора маршрутов надолго нельзя,
это путь к рассинхрону вроде dd94139b.

## Что дальше

Курированный список (200–400 префиксов ключевых RU-сетей вместо geoip-дампа)
даёт ~800 маршрутов и прямой доступ ко всем практически нужным сервисам.
Автоинверсия оптимизирует не ту метрику: в бюджет попадают широкие абонентские
пулы операторов, а банки и госсервисы живут в /19../24 и выпадают первыми.

## Отвергнутые альтернативы

- **Огрубление префиксов (floor)** — при равном бюджете покрытие в разы хуже.
- **`excludeRoute()` (API 33+) сам по себе** — exclude-записи попадают в тот же
  `LinkProperties` как `RouteInfo`; parcel уменьшает только меньшее ЧИСЛО записей.
- **Решение direct/tunnel внутри датапаса** — перенос killswitch из ядра в наш
  код, потеря ICMP/multicast/LAN, разрыв сессий на флапах. Отложено.
